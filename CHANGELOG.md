# Changelog

## Unreleased

### Added
- Custom media uploads in the Game Details Media tab: add preview images from local files, a drag-and-drop zone, or an image URL, with live progress. Previews can be reordered by drag and the order persists in a new `preview_sort` table keyed by remote URL (or relative path for custom uploads), so it survives re-downloads, stream/download switches and metadata refreshes. Previews now carry a source logo and a storage-location badge, and custom previews can be deleted independently of downloaded ones.
- Add Buzzheavier host support (`buzzheavier.com`, `bzzhr.to`, `bzzhr.co`). The download route is behind a Cloudflare challenge, so the resolve runs in a browser window: it clicks the htmx download button, captures the `HX-Redirect` (or an attachment via `will-download`), and hands the resolved CDN link plus the browser's own cookies/UA back to the downloader. The resolve partition is persistent so a solved challenge survives a restart -- only Cloudflare's own challenge cookies are kept, everything else is stripped after each resolve -- and resolves run one at a time, since a shared session cannot carry two concurrently. Each time your IP changes there is a brief auto-resolve window while the challenge is re-solved.
- The version readout in the topnav and sidebar is now a button that opens that version's GitHub release page. The tag it builds matches what the release workflows publish -- `v<version>` for stable and `v<version>-nightly.<run>` for nightly -- so it lands on the real release rather than a 404. (#143)
- Added a "Download Version" entry to the split-button caret on the game detail page, beside "Manual Install". It opens the same downloads modal the UPDATE button does, listing every build and mirror the thread offers, so a different version can be fetched over one already installed. Previously an installed title with no pending update had no route to that modal at all: the primary button becomes PLAY once a version is installed, and the UPDATE button only renders when an update is flagged. The entry goes straight to the downloads modal rather than through the source picker, and is shown disabled with a reason for titles with no F95zone thread linked.

### Fixed
- Allow Win download links to show up for Linux platform since Linux can run both Linux version and also use Wine to run Win executable.
- Fixed `hasLocalPreviews` and `hasLocalBanners` missing already-downloaded assets, so a `missingOnly` media refresh re-downloaded images that were already on disk. Both now query `media_assets` and the `previews`/`banners` tables, which is what the delete paths already did.
- Custom preview uploads now accept images only. The file picker filters to image types, the drop zone rejects anything else with a message, and the main process re-checks the extension before copying -- neither of the first two is a guarantee, and an unrecognised file copied into `data/images` became a preview tile that could never render. URL fetches are restricted to http(s), capped at 64 MB, throttle their progress events, and clean up the partial file if the download fails.
- Fixed the Downloads and Collections pages being clipped to one screenful. Both are mounted in a shared pane that is `overflow-hidden` for every non-detail view, and neither carried a scroll container of its own -- a stale comment claimed `#gameGrid` scrolled them, but it is not in that path at all, so entries below the fold could not be reached. Downloads is now a flex column with a pinned header above a single scrolling list; Collections scrolls its grid. On Downloads the scrollbar stays hidden until you scroll or move near the right edge, driven by a class rather than a CSS `:hover` rule so it does not appear anywhere over the list. Scoped to those pages; other scrollbars are unaffected.
- Fixed the download list dropping whole sections of a thread and mislabelling the rest. Two causes. An "Extras" heading inside one build's block latched the parser into its extras bucket for the remainder of the post -- only a literal "DOWNLOAD" heading cleared it -- so on a thread like Thief of Hearts every link under "Part 1" (MEGA and Pixeldrain included) was filed as an extra, and extras are never passed to the download modal. Separately, "Part 3" read as an archive fragment marker rather than a build name, and a fragment is cleared by the platform line beneath it, so the build name was gone before any link was reached: Part 3 came out unlabelled and Part 2's rows inherited "Part 1 & 2" from the spoiler header above them. The line alone cannot tell the two readings apart, so the parser now decides by what follows it -- a platform with no link in between means it named a build, a link first means it was a fragment marker. The download classifier ran its own "Part N" regex over the group text and re-read those build names as fragments of one split archive, assembling Parts 1-3 into a single set that required all three, so no part was offerable on its own; it now trusts the parser's reading when the parser supplied one, and keeps the regex only for callers that never had the field.
- Fixed the colour pickers in the Banner Editor's Layout tab closing as soon as the colour changed, so the slider and shade square could only be click-selected and never dragged open. The per-field editor (`Inspector`) was defined *inside* the editor's render body, which makes React treat it as a new component type on every re-render; the first `onChange` re-rendered the editor, remounted the whole inspector, and destroyed the `<input type="color">` the native dialog was bound to. `Inspector` is now module-scope and takes its state as props, so its identity is stable and the picker stays open through a drag. Size & Image and Panels tabs were unaffected.
- Fixed Playtime Formatting & Badge Unit Bug: Standardized playtime logic across the game detail page and library banner badge by fixing unit conversions (treating database values consistently as minutes) and implementing proper ceiling rounding for fractional times to prevent improper displays like "1h 60m" or 0.4 minutes showing as "Not played". The banner editor and preset preview samples were carrying a seconds-era playtime constant and are corrected to minutes.
- Implement add/remove wishlist in Browse mode context menu that trigger `toggleWishlist` action for non-local rows, Using optimistc UI approach to dispatch the db update, and the success broadcast triggers the renderer so grid view without triggering full refresh. The `wishlist-updated` broadcast is now source-tagged: context-menu toggles skip the catalog refetch (optimistic UI already flipped the row), while the extension path keeps it (no optimistic UI exists there). The broadcast fires on every outcome so a failed write reconciles the optimistic flip, and a `wishlistOnly` Browse filter still refetches because its row set is decided server-side.
- Fixed slow "wishlist only" filtering in Browse and Library by 1. Adding indexes on columns used in query and 2. Splitting a single multi-OR subquery into separate EXISTS clauses.
- Fix and remove the redundant isWishlistEntry memory flag which was set but never unset and cause unexpected behavior on entry display regarding wishlist. The isWishlisted logic will check the data from wishlist_entries instead. Note: the IPC behavior is not related and not updated.
- Remove the 'has Steam mapping' quick filter
- Fixed the library grid (banner view, Browse and Wishlist) nesting two scroll containers. `#gameGrid` scrolled while the virtualized grid inside it scrolled as well, so the working scrollbar sat a scrollbar's width in from the right edge with an empty track beside it. `#gameGrid` is now a flex column -- status banners are fixed rows and the pane below them is the only scroller -- and the grid's column count budgets for its own scrollbar, whose width now comes from a single `--scrollbar-size` shared by the CSS and the layout arithmetic. Status banners stay pinned at the top instead of scrolling away with the grid.
- Fixed the Settings > Database tab nesting a second scroll container inside the Settings shell, which put one scrollbar inside another so the working one sat a scrollbar's width in from the edge with an empty track beside it. Every other settings tab already left scrolling to the shell.
- Fixed scrollbars being nearly invisible, worst on 4K displays and under fractional Windows display scaling. `main.css` set both the standard `scrollbar-width`/`scrollbar-color` properties and the `::-webkit-scrollbar` pseudo-elements; since Chromium 121 the former makes Chromium ignore the latter entirely, so the themed 12px scrollbar was dead code and what actually rendered was `scrollbar-width: thin` -- a hairline that rounds down to almost nothing at high DPI. The standard properties are gone and the pseudo-element styling is live again, giving an explicit 12px that scales predictably and that `scrollbar-gutter: stable` reserves exactly.
- Fixed saved Browse filters losing their sort order. A saved filter is normalized on both sides of the IPC boundary, and the main process copy in `electron/ipc/settings.js` had been left at the four legacy values (`nameAsc`, `nameDesc`, `newest`, `oldest`). Twelve of the sixteen sorts were therefore rewritten to `nameAsc` on save and reloaded as title A-Z -- including `threadUpdatedDesc`, the default, so even an untouched filter came back re-sorted. The vocabulary now lives in `electron/utils/savedFilterSort.js` for the main process and is exported from `src/hooks/useFilters.js` for the renderer, with tests asserting the two agree on the sort list, the legacy aliases and the default.
- Fixed the Personal Rating on the game detail page counting unrated categories as a score of zero, which dragged the average down (rating two categories 8 and 6 showed 1.75 rather than 7) and disagreed with the figure `RatingModal` displayed for the same game. The page had a private copy of the averaging rule; it now calls the shared `computeRatingAverage` it was already importing, so the detail page, the rating modal and the database all apply one rule.
- Update global lightbox control for media in lightbox instead of only under GameDetails.
- Fixed browser extension thread matching comparing numeric IDs across sites without validating the host domain source (F95Zone vs LewdCorner). F95Zone threads with ID `X` were erroneously matched against games that only carried LewdCorner ID `X`. Thread lookup is now strictly site-isolated (`f95Id` for F95Zone threads, `lcId` for LewdCorner threads).
- Fixed `open-game-folder` IPC handler opening the parent directory of the game folder instead of the game directory itself (`selectedVersion.game_path`).
- "Open Game Folder" was missing entirely from the context menu of every Steam and GOG title, and so was Play. Both rows were built from one list filtered as `versions.filter(v => v.exec_path && v.hasExecutable !== false)`, and Steam and GOG versions are stored with an EMPTY `exec_path` by design -- they launch through `steam://run` and `goggalaxy://openGameView`, see the `upsertVersion` calls in `electron/ipc/importer.js`. So the filter removed those titles before either row existed. The submenu was correct; nothing ever reached it.
- The `hasExecutable` half of that filter never did anything at all. It is a local inside `launchGame` and has never been a field on a version object in the renderer, so the clause read `undefined !== false` on every version ever passed through it.
- Play and Open Game Folder are built from separate lists now, because they answer to different rules and one list could only ever satisfy one of them. Play takes versions that can actually launch; Folder takes versions with a path recorded, whether or not it is currently there.
- Opening a folder no longer goes through `getTrustedVersion`. That helper asks "is this version installed", which is the right question for launching and the wrong one here -- launch needs an executable, a Steam appid or a GOG id, and its handoff branches never touch `game_path`, while opening a folder needs one thing: a directory on disk. Sharing the gate meant Steam and GOG versions were judged by rules written around executables.
- Those rules also disagree with each other. `getGames` force-installs Steam on `steam_id && isSteamInstallPath` and GOG on `gog_id && (in_place || game_path)`; `getGame` has the Steam branch only; `getVersionForRecord` -- the one `getTrustedVersion` actually calls -- joins only `steam_mappings`, so it never selects `gog_id` and has no GOG branch to disagree with. Left alone deliberately: the new path does not consult any of them, and unifying them would have changed launch behaviour, which this PR is not about.
- A folder that could not be opened was indistinguishable from a menu item that did nothing. `ipc/windows.js` ended in `.catch(err => console.error(...))`, writing to a console the user does not have open; `ipc/games.js` returned `{success, error}` that `GameDetailPage` discarded. On top of both, `shell.openPath` RESOLVES with an error string rather than rejecting, and neither call site inspected it -- so a path that did not exist reported success.
- Version identity is `version_id` rather than the version string. `versions` has `UNIQUE(record_id, version)` so the string is usually unambiguous, but `clientAudit` counts duplicate version rows on legacy databases and reports them as "not auto-repaired", and SQLite treats NULLs as distinct under UNIQUE, so blank labels slip past the constraint entirely. Both cases resolved through `ORDER BY date_added DESC LIMIT 1` -- silently, to whichever row sorted first.
- `handleContextAction` dropped `source` and `sourceAppId` when forwarding to `launchGame`, unlike the `launch-game` IPC handler beside it. `launchGame` then fell back to `getSteamIDbyRecord`, which resolves the TITLE mapping -- so a title holding two Steam versions launched whichever one that pointed at, regardless of which version was clicked.

### Added
- `electron/library/gameFolder.js`. Resolves and opens one version's folder, with dependencies injected so it can be exercised without an Electron runtime. It reads `game_path` and nothing else -- not `source`, not `source_app_id`, not `in_place`, not `exec_path` -- which is what makes it work for Steam, GOG and F95 without a branch for any of them.
- `getVersionById(recordId, versionId)` in `db/versions.js`. Returns the raw row and makes no install judgement, so nothing downstream can mistake it for one. `record_id` is in the WHERE clause rather than carried alongside it: `version_id` is a bare rowid (`versions` has no INTEGER PRIMARY KEY), and SQLite does not guarantee rowid stability across the `VACUUM` the client audit runs, so scoping the lookup means a rotated id resolves to nothing rather than to another game's folder.
- `src/components/detail/page/VersionCard.jsx`. Extracted from `GameDetailPage`'s render, where the card was ~40 lines of JSX inside a `.map` inside an 1800-line component that nothing could mount. The folder button could not have been asserted without it.

Written first: 12 of 15, both new modules, and 3 of 5 failed against the unfixed branch. The rest pass either way, which is what makes them guards.

### Not done
- **The three install rules are still three.** `getGames`, `getGame` and `getVersionForRecord` continue to disagree about when a Steam or GOG version counts as installed. Nothing on the folder path consults them any more, so the bug being fixed here is gone, but a version the library lists and `launch-game` refuses is still reachable. Unifying them changes launch behaviour and belongs in its own PR.
- **`games.selected_version_id` persists a rowid.** Same VACUUM exposure as any other stored `version_id`, and it predates this change. Noted rather than fixed.
- Fixed missing {engine} and {f95Id} for downloads-install handler. Previously it only work during nomral importer, but shown Unknown or empty when set in Atlas Library Structure during downloads-install process. 
- Fixed personal rating modal (`RatingModal`) resetting its draft state to the database ratings when background metadata updates or library refreshes occur while the modal is open.
- Fixed rating displays on library and catalog card overviews to format consistently on the 0–10 scale (`/10`), resolving an issue where ratings at or below 5 were mislabeled with a `/5` denominator (#321).
- The browser extension still did not reach disk after the previous fix. That fix was correct as far as it went -- `asarUnpack` put the files at `resources\\app.asar.unpacked\\extension` and the candidate ordering found them -- and the copy then failed at the DESTINATION, which nothing had looked at.
- `ensureExtensionFiles` targeted `path.join(appDataRoot, 'extension')`, and on Windows `appDataRoot` IS the install directory: `dataLocation.js` `resolveDataRoot` returns `installDir` on win32. So the target was `C:\\Program Files\\Atlas\\extension`, and every copy failed with EPERM.
- That is not a permissions oversight to be worked around -- it is a deliberate decision, and the right one. `build/installer.nsh` grants the Users group modify rights on `$INSTDIR\\data` and `$INSTDIR\\launchers` and explicitly NOT on `$INSTDIR` itself, because that folder holds Atlas.exe; a user-writable directory of executables that something elevated later runs is a privilege-escalation route. Atlas runs unelevated after install for the same reason: it launches game executables, and a child process inherits its parent's elevation.
- The target is `dataDir` now -- `<installDir>\\data\\extension` -- which is where every other piece of runtime state already lives (config.ini, images, logs, the database) for exactly this reason. It also survives upgrades: `installer.nsh`'s `DeleteLoop` wipes every `$INSTDIR` subfolder except `data` and `launchers`, so even a writable `$INSTDIR\\extension` would have been deleted by the next installer run, taking with it the folder Chrome was pointed at.
- This looked like a regression from the per-machine switch and was not. The older `perMachine: false` builds installed into `%LOCALAPPDATA%`, which IS writable, so the wrong path happened to work there. Any stale copy left at the old location is removed by the next installer run.
- The folder was also created lazily, by the three IPC handlers -- all of which sit behind a settings screen the user has to go looking for. Someone who installed Atlas and went straight to Chrome's "Load unpacked" found nothing there, with nothing having gone wrong from Atlas's point of view. `registerExtensionHandlers` syncs once at startup now; the mtime check means the copy itself is skipped on every launch after the first.

## Unreleased

### Fixed
- A Steam mapping took the INSTALL button away from every other source. `resolveActionBarRoutes` had `hasSteamInstall ? 'steam'` at the top of its priority chain, so a title with both a Steam appid and F95 mirrors could only be installed from Steam -- and the mirrors were not hidden or greyed, they were UNREACHABLE. The one control that opened them now did something else under the same INSTALL label, so nothing on screen said a decision had been made.
- The rule is the source COUNT now, not which sources they are. More than one is a choice and opens a picker; exactly one goes straight there, which is the part of the old behaviour that was right -- Steam-only still hands off to Steam with no dialog in the way.
- The rule existed TWICE, and only the second copy drove the button. `resolveActionBarRoutes` returned `installRoute`, and then `ActionBar` derived its own `steamInstallCta` in the component body and used that for both the click handler and the label. The routing function could have been entirely correct and the button would still have handed off to Steam. The file's own header comment says routing was centralised so it would not be "a chain of || inside JSX"; `steamInstallCta` was then written as exactly that, in the same file, six lines below the call.
- `tests/action-bar-routes.test.js` asserted the bug: "lets Steam take the install button when it owns the title". Replaced rather than deleted, so the contract that superseded it sits where the old one was.
- The browser extension shipped in the installer but never reached disk. Two independent faults, both invisible in dev.
- `extension/**/*` was in `build.files` but not `build.asarUnpack`, so it went inside `app.asar`. Chrome cannot load an unpacked extension from there, which is the whole reason `ensureExtensionFiles` copies it out.
- That copy used `fs.cpSync`, which cannot read across an asar boundary. Electron's asar support works by patching the PUBLIC `fs` module; measured on the Node 22 in `.nvmrc`, the only public method `cpSync` calls is `lstatSync` -- `readdirSync`, `copyFileSync` and `mkdirSync` all go to internal bindings that bypass the patch, see `app.asar` as a file rather than a directory, and throw. The `catch` swallowed it, `ensureExtensionFiles` returned the target path anyway, and `get-extension-path` reported a folder that had never been written.
- The candidate list made it unrecoverable: `candidates.find(fs.existsSync)` takes the first hit, the first entry was the in-asar path, and `fs.existsSync` IS patched -- so it returned true and the three real-directory fallbacks below were never tried. Real directories are searched first now, `app.asar.unpacked` at the head, with the asar path kept last as a fallback.
- Both only ever broke in packaged builds. In dev `app.getAppPath()` is the project root, so the first candidate was a real folder and there was no asar to cross, which is why this survived every run on a developer machine.

### Added
- `src/components/detail/page/installSources.js`. Resolves which sources a title can be installed from, so the list can be asserted rather than inferred from a boolean. `hasSteamInstall` could only ever express "Steam, or not Steam", and a flag with two states can only answer a three-way question by overriding one of them.
- `InstallSourceModal`. Lists the available sources, ordered by `Metadata.sourceOrder` -- the same key that orders media resolution, so a user who put Steam first sees Steam first. Not shown for a single source: a dialog whose only purpose is to have one option clicked is a step, not a choice.
- Sources removed from `Metadata.sourceOrder` are excluded. Someone who took Steam out of their sources has said they do not want Atlas treating this as a Steam game, and offering a Steam install anyway would be the same override in the other direction. An unset key means every source; an empty string means none -- those are different states and collapsing them would either ignore a deliberate choice or hide everything from someone who never made one.
- GOG is offered only when there is a store page to open. There is no `gog://` equivalent of `steam://install`, so without a URL the entry would be a button that does nothing. Its handler is separate from the toolbar's `openGog` despite going to the same place today: one is a link and one is an install route, and folding them together means the day GOG grows a real handoff, changing one changes the other.
- LewdCorner is never offered. It is a metadata source but `UpdateModal` fetches by `f95_id` and there is no LewdCorner download path, so listing it would be an option that cannot be taken.
- Manual Install stays on the caret and is deliberately not in the picker. The dialog answers "where do I get this game"; an archive already on disk is a different question. A second route to the same panel would also make the caret look conditional, which is the shape of the bug the caret was introduced to fix.
- `tests/install-source-routing.test.jsx` (7). Mounts `ActionBar`, which the resolver's own unit tests cannot do -- and that is the point: three of the seven fail against the pre-fix component and four pass either way, which is what makes those four guards. Verified by restoring the old `steamInstallCta` in a scratch tree and confirming exactly those three flip.
- `scripts/check-extension-packaging.js` (7), wired into `npm run check`. Nothing asserted anything about `build.files` or `build.asarUnpack` before, which is precisely the gap this fell through. It also MEASURES the `fs.cpSync` constraint rather than citing it, so if a future Node routes `cpSync` through the public `fs` module the check fails and someone gets to delete a workaround instead of inheriting it forever.
- The manifest is cross-checked against the files on disk, so a `manifest.json` naming a script that was never committed fails here rather than producing an extension Chrome refuses to load.

### Changed
- `ActionBar` looks its handler up in one map keyed on `installRoute`, so the click and the label cannot disagree. The Steam glyph now appears only when Steam is the sole source, where it describes where the button goes; with several sources it read as a decision already taken.
- `resolveActionBarRoutes` takes `installSources` in place of `hasSteamInstall`, and returns it, so the label reads off the same value that drives the click.

### Not done
- **No test that the packaged output actually contains the extension.** `check-extension-packaging.js` asserts the config that produces it, not the artifact. Catching the real thing means unpacking a built `app.asar`, which needs a full `electron-builder` run.
- **`ensureExtensionFiles` still reports success it cannot vouch for.** A failed copy logs and returns the target path; callers then test `fs.existsSync` separately. Better would be for it to return the outcome, but that changes three IPC handlers and was not worth folding into this.

### Added
- `LibraryFolderModal`. Raised two ways for two different situations: ahead of the install when the setting was already empty, and reactively on `step: "no-library-folder"` when the folder was cleared between that check and the attempt. Only the main process can tell those apart, so the renderer branches on the step `fail()` reports rather than on its prose. The item stays in `install_failed` with the archive intact throughout, so retrying costs a click.
- `LibraryStructureModal`, shown once before the first install. `Library.libraryFolderStructure` defaults to `{creator}/{title}/{version}`, which nests every install three levels deep -- a real decision that was being applied silently, and one a user only discovered after their library was already built the other way. ### Added
- MEGA is a download host. Anonymous public-link downloads, no account needed -- MEGA's public-link API takes no authentication at all, because the link *is* the credential: the decryption key travels in the URL fragment and never reaches MEGA's servers. An account only raises the transfer quota, so signing in is additive and this works without it.
- `electron/downloads/hosts/megaLink.js`: link parsing and key derivation, pure and offline-testable. Handles the current `/file/<id>#<key>` form and the legacy `#!<id>!<key>` still posted in old threads, on both mega.nz and mega.co.nz. A 43-character fragment decodes to exactly 32 bytes: halves XOR to the AES-128 key, bytes 16-24 are the nonce, 24-32 the expected meta-MAC. Verified against a real link before any of it was written -- the derived key decrypts that file's attributes to `MEGA{"n":"<filename>"}`, and the `MEGA` prefix is MEGA's own key check, so its absence means the link's key does not match the file rather than that the response was corrupt.
- The API call sends ONLY the file id. Sending `id#key` as the `p` parameter returns `[-2]` (EARGS), which is how this was first got wrong. MEGA reports failure as a bare negative number rather than an object, so `classifyError` switches on that: `-17` is quota, `-9` and `-11` fatal, `-3` and `-4` transient.
- Folder links are RECOGNISED rather than rejected as malformed, so the plugin can say "open the folder and copy the file's own link" instead of "that is not a MEGA link". Folder support needs the tree fetched and decrypted first, which is its own piece of work.
- A remote filename can no longer become a path. MEGA supplies the name and the manager joins it onto the downloads directory, so separators become underscores and leading dots are stripped -- which also stops a download landing as a hidden file.

### Changed
- `electron/downloads/downloadManager.js`: the plugin contract gains an optional `decrypt` descriptor. MEGA serves AES-CTR ciphertext, so unlike every other host there is no URL that yields the real file and the "translate the page url to the file url" shape does not apply. Rather than give MEGA a private downloader -- a second copy of the resumable-transfer, progress and cancellation logic, which the contract's own comment exists to prevent -- a plugin returns a transform descriptor and the manager pipes the response through it. The manager still owns the transfer.
- `electron/downloads/hosts/megaDecrypt.js`: the decrypting transform, computing MEGA's integrity MAC as the bytes pass. The MAC is a CBC-MAC per chunk folded into a file MAC and condensed to the 8 bytes the link carries, over chunks that grow 128KB at a time to 1MB and then stay there -- the progression is part of the MAC definition, so a wrong boundary fails a file whose bytes are perfectly correct.
- Resume works because AES-CTR is seekable: byte N depends only on the counter for block N/16. An offset that is not block-aligned is REFUSED rather than accepted, because the alternative is a file of noise that passes every length check the completion step makes.
- The MAC is not resumable the same way -- it is sequential over the whole file -- so a resumed transfer reports `null` from `verify()` rather than `false`. "Not verified" and "failed verification" need different messages and must not collapse into one boolean.
- Verification happens in the manager's existing `verifying` state, because the MAC is only knowable once the last byte lands. A large file can therefore transfer completely and still be rejected, and the message says the bytes are corrupt rather than something generic -- by every other measure the file looks finished.
- `tests/mega-host.test.js`: 35 tests. The vectors are SYNTHETIC on purpose: committing the real key used to develop this would publish a working download link for someone's file in git history forever. What no test here covers is a real transfer against MEGA's servers -- the round-trips prove the implementation is self-consistent, not that it matches MEGA's spec.
- `scripts/check-host-plugins.js`: the assertion that mega.nz was rejected for having no plugin is inverted, which is what demonstrates MEGA links now reach the mirror list.
